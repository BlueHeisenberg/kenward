kenward

A household AI assistant where each person’s memory is actually their own.

kenward is a self-hosted assistant for a family or a group of friends. Everyone talks to it through Telegram — privately, or in a shared group. What it remembers about you privately stays private; what the group teaches it is shared with the group. That boundary is separate stores, separate keys and separate processes — not a WHERE user_id = clause you have to take on faith.

It runs on hardware you already own, routing each request to whichever of your machines is awake, and falling back to a cloud provider only where you allow it.

Status: released. Binaries for Linux, macOS and Windows, a container image, .deb and .rpm packages, and a signed update manifest, on the releases page. It has not yet run a household for a week, so treat it as a first release rather than a settled one. The binaries are unsigned: macOS needs right-click → Open the first time, and Windows will warn until the code-signing certificate exists.

The gap it fills

Personal assistants are built for one person on one box

Add a second human and you get one of two bad outcomes: a single shared brain that leaks everyone’s private context into everyone else’s conversations, or separate installs with no shared knowledge at all. Neither is what a household wants. A family wants the assistant to know that Tuesday is bin day and that the boiler code is 4471, while not telling your brother what you asked about last night.

Doing that properly means per-person identity, cryptographic separation, invites and multi-device sync — the boring, expensive half of the problem. That half already exists in lore, so kenward is the assistant loop on top of it rather than a memory system built from scratch.

The memory model

Two kinds of memory, and one asymmetry

Private memory is what the assistant knows about you: preferences, ongoing concerns, the shape of your week. It is a lore space with exactly two members — you and the node.

Shared memory is what the household knows collectively: house logistics, recurring plans, decisions everyone should be able to recall. A lore space with every member in it.

The same thing in words.
ConversationReadsWrites

Household group chat shared space only shared space
Direct message with kenward itself shared space only shared space

The diagram above is a household with one assistant, which is the default and has two kinds of conversation. The third row is the other arrangement: a household can give every member an agent of their own, and then kenward is the household’s own agent, reachable privately as well as in the group. That private chat with kenward reads and writes the shared space and nothing else — it is where you add to the household’s memory, or ask what is in it, without doing it in front of everybody. It never touches your private memory. Knowing who is asking is not permission to read them.

Private conversations can read shared memory, because that is useful — you should be able to ask when the bins go out. Group conversations can never read private memory, because that is the entire point. Copying something out of a private space into the shared one is an explicit, reviewed act that shows you the full text before it is published.

Nothing is written to memory silently

A note to your own memory is written and then shown to you — the exact words, the space it went to, and an Undo button live for a few minutes. Anything bound for the household’s shared memory is proposed first and written only if you say yes, because publishing to everybody is the one act here that cannot be taken back. A household that prefers to be asked about its private writes too sets capture.private_writes: ask; there is no setting that makes a write silent, and that is the part with no configuration option.

A group conversation is never offered a private destination, and only the member who was asked can answer — in a group chat everyone can see the buttons, and without that filter somebody else could route your memory for you. A proposal that times out counts as declined; an undo window that times out leaves the write standing, and says so.

Two modes, one binary

The setup question is about trust, not topology

Which mode you run is chosen once, during setup, by answering one question: does everyone here trust whoever runs this machine to be able to read their private conversations? A non-technical installer can answer that. They cannot answer “do you want per-user pods?”, and the pods are a consequence rather than the decision.

It is the only question setup asks about security. The other one that sounds like it — one assistant, or one each — is about presentation, and neither the wizard nor this page lets them be conflated.

The assistant loop, the memory policy, the routing and the capture flow are identical in both. Only the supervisor differs.

Simple mode is honest about being simple. Separation between members is real, but sealing against the machine’s owner is not. Most households are fine with that — it is their own family — and it is by far the easiest thing to run. The ones that are not fine with it have Isolated mode, which is not a paid tier: it is the mode that makes the privacy claim true, and charging for that would be gating the wrong feature.

Isolated mode gives each member their own bot token, because encryption at rest does nothing for the channel: whoever holds a bot’s token can read every message sent to it. That costs about five minutes of setup per person.

Inference

Runs on whatever is awake

Most people with a local-inference habit have a scatter of machines: a GPU workstation, a laptop, a mini PC, none of them on all the time. kenward treats them as a pool. Endpoints carry tier tags, each space declares the tiers it may use in order, and requests load-balance within a tier and fall through to the next when a tier has nothing reachable. A machine that is powered off is skipped in about two seconds rather than hanging the conversation.

Cloud providers are just another tier — one you opt into per space. When the chain is exhausted, kenward refuses. There is deliberately no code path that widens a chain: no default, no fallback, no “if nothing matched, try everything”.

A private space configured local-only will tell you no local machine is available, naming the tiers it was allowed and the endpoints that could not answer, rather than quietly shipping your private context to a provider. That is the difference between claiming privacy and having it, and it is a configuration line rather than a subsystem.

What it needs

Three things, and only one of them is software

  • A machine that is always on

    A mini PC, a NAS, an LXC container on a Proxmox host, a desktop that never sleeps. It holds no GPU and costs effectively nothing to keep running. It needs no inbound network surface, no port forwarding and no VPN.

  • A Telegram bot

    Message @BotFather, send /newbot, follow two prompts, keep the token. Then, in the same chat, send /setprivacy, choose the bot and choose Disable — Telegram turns privacy mode on for every new bot, and with it on the bot receives nothing at all in a group chat: not plain messages, not a reply, not an @mention, and nothing is logged because nothing arrives. Do it before adding the bot to any group; Telegram applies the change only to groups joined afterwards. Setup asks Telegram whether it is off, says so plainly if it is not, and offers to check again while you are still standing there; kenward doctor checks it again later. Members need no client software beyond Telegram, which they already have.

  • Nothing else installed

    kenward keeps its own memory. It imports lore as a Go module, opens the store inside its own process, and creates that store the first time it runs if this machine has never had one — no lore binary to fetch, no lore init, no server, no protocol between them. Both wizards make the household’s shared space and one private space per person and write their ids into kenward.yaml themselves, so there is nothing to copy between two programs. A machine that already runs lore has kenward add its spaces to the store already there. (The exception is an isolated household of several pods: each pod runs lore’s lore serve --lan to carry the shared space between them, so those images need the binary.)

  • At least one inference endpoint

    Anything OpenAI-compatible: vLLM, llama.cpp, Ollama, LM Studio, or a cloud provider. It does not need to be awake during setup — kenward is built for machines that are usually asleep.

One household runs one deployment. There is an admin dashboard — one HTTP server, one account, bound to loopback unless you say otherwise, with a first-run wizard that can set the whole household up in a browser instead of a terminal. There is no multi-tenant runtime, no control plane, no SSO, no organisations and no usage quotas — none of it is designed around, and most of it is never going to exist.

Installing

One binary, two questions

Setup asks two questions that shape the household. The first is about security: does everyone here trust whoever runs this machine to be able to read their private conversations? That is the one that chooses the mode. The second is about presentation: one assistant for the whole household, or one each? A member’s own bot is a separate contact, not a separate secret — and because one bot is one contact is one agent, one each needs Isolated mode’s per-member bots, which setup says rather than quietly handing everybody the same assistant under several names.

Simple mode, Linux

curl -L https://github.com/BlueHeisenberg/kenward/releases/latest/download/kenward_linux_amd64 -o kenward
chmod +x kenward
sudo mv kenward /usr/local/bin/
kenward setup

macOS and Windows download the matching artifact and run kenward setup the same way. There is a systemd unit and a Compose file in the repository for running it as a service.

Isolated mode

Linux only, and it needs Podman or Docker — the isolation is the container runtime, so there is no meaningful equivalent elsewhere. Setup says so if you pick it on the wrong platform, rather than failing later.

Adding people

kenward invite --name "David"

prints a single-use code that expires in 24 hours. They message the bot and send it. Until they do, the bot will not reply to them at all — not an error, not a prompt, silence. A bot username is publicly discoverable, and any reply would confirm to a stranger that there is something here.

Checking it works

kenward doctor

reports configuration, memory, transport and every endpoint, and then prints what your chosen mode actually promises about privacy — including, in Simple mode, that the operator can read every member’s private memory. A powered-off endpoint is reported as a fact, not a failure.

The full procedure, including secret handling and the caveats that apply while this is being finished, is in INSTALL.md.

Where the claim stops

What kenward does not promise

A model must see plaintext to answer. A server-side assistant therefore cannot be end-to-end encrypted with respect to its own server, and no arrangement of keys changes that. So the claim is not “the operator cannot read your memory”. It is: the operator cannot read it from disk, from a backup, or while you are not in session, and doing so requires deliberately attacking their own family. That is strong, checkable and true. The stronger version is neither.

  • The node can read private spaces at all. That is what being the second member of a two-member space means, and it is the price of an assistant that answers when your laptop is closed.
  • Root always wins. An attacker with root on the host during an active session reads the unwrapped key out of memory. Isolated mode raises the cost; it does not create an impossibility.
  • In Simple mode the operator can read everything — every member’s private memory, at rest and in flight. That is the mode’s known limitation, not a bug, and kenward doctor says so out loud.
  • A delete is a tombstone, not a shred. Undo really does remove an entry: it stops coming back from search and from get, here and on every synced device. The row is still on the disk. That is lore’s model, it is what makes a delete survive a sync, and it is why publishing something from a private space into the shared one shows you the full text first — unpublishing is not the same as never having published.
  • The privacy differentiator is a property of self-hosting. Isolated mode on somebody else’s infrastructure seals nothing against that somebody else.
